# PR #5 审核整改：源码、计算与交付证据的绑定

审核对象为 `9b2b5b03b43fff7156a0d9ce73b4063603fed40e`。评审提出的源码校验缺口和无Git复现问题成立；第三项关于单因素、联合扰动及实物验证的区分继续保留。

## 根因核对

原计算记录 `6ab665b`、报告/审计代码记录 `7efdef2`，最终结果提交为 `9b2b5b0`。逐一比较原manifest的10个追踪文件：工作区原始字节哈希全部与记录一致，10个文件的Git文本从计算提交到审核head均未改变；其中7个文件的Git blob为LF，而运行工作区使用CRLF，因此直接对Git blob与工作区原始字节求哈希会得出不同值。

这组证据说明“提交号不同”不能单独证明数值代码改变。不过，旧导出函数仅核对结果文件，没有验证当前源码；原追踪列表也未覆盖共享归档模块。该漏洞允许修改源码后继续输出旧结果，必须修正。另在项目外运行 `git rev-parse HEAD` 返回128，旧入口确实不能直接用于无Git目录。

## 采用的修正

1. 增加 `q1/provenance.py`，明确13个计算依赖文件（包括共享归档与校验模块、配置、锁定依赖），记录原始字节SHA256以及统一CRLF→LF后的SHA256和集合摘要。任何其他内容改变都导致检查失败，不以重新格式化、注释或自动调整参数规避源码绑定。
2. 文本产物的便携校验也声明 `sha256-text-lf-v1`；NPZ、PDF、Excel等二进制产物仍按原始字节校验。原始题面和附件哈希不改变。原基准还记录原始字节哈希，检查本轮运行期间确实未被改写。
3. 生产计算开始/结束、单组缓存、正式报告和审计均检查源码指纹；各组run与总manifest必须使用相同计算摘要。源码不匹配时停止导出，旧格式归档不会被静默认定为当前验证结果。
4. Git只提供辅助的计算提交信息。缺少Git、目录不是仓库或只是位于其他仓库的子目录时记录null，依靠完整源码摘要保持可追溯，不借用外层仓库提交。
5. 将临时审计脚本改为入库入口 `python -m q1.sensitivity_audit`。审计核对当前计算源码、报告生成器、测试源码、各组原始数据及复现记录；默认只读，`--run-tests --write`可重跑测试并写出新的审计记录。

先提交修复后的计算代码，再重新运行33次积分及一次独立复现，更新manifest/run/export/audit。结果文件提交必然发生在运行之后，因此它的Git提交号与计算代码提交号可以不同；当前head是否适用这些结果由入库源码的完整摘要逐文件验证，不能靠反复改写提交号制造“head等于自己”的循环记录。

## 审核与验证口径

新增测试覆盖无Git可执行程序、非Git目录、拒绝借用父仓库、CRLF/LF等价、其他源码编辑被阻止、遗漏依赖文件被阻止、旧结果不能在变更源码下导出。真实无Git打包环境的运行与最终审计另随结果记录，尚未执行时不以这些测试代替。
